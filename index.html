Coding agent? Install the adversarial-review skill into your agent's skills dir and say run an adversarial review.

It is one file at the repo root that declares how adversarial review is done in that repository — which lenses, what counts as evidence, how severities are assigned, how a challenger disputes the reviewer's findings, and how the disagreement is reconciled — so any agent that reads it stops rubber-stamping its own output. Green CI proves the code does what its author imagined testing; this standard exists because agents now write code faster than humans can review it, and review has to be declared, evidence-backed, and machine-readable to keep up.

The standard is versioned, MIT licensed, and governed in the open. Changes go through a public process — issues before pull requests, cryptographically verified commits, recorded signoff on every merge — and anyone may participate. No vendor controls it, and no adopter must accept it unchanged: take the protocol, customize the repo-specific section, and propose improvements back to the community.

For the execution side of agent work, pair this with Loops and Graphs. It is a super agent harness: every task gets a deterministic check, independent steps run in parallel, and the human only approves the final merge.

The idea

One file that makes review adversarial

  1. Drop an ADVERSARIAL_REVIEW.md in your repo root.
  2. It tells any coding agent: your work here is expected to survive adversarial review — and here is how that review is done in this repo.
  3. A reviewer R proposes findings pass by pass, one lens at a time, with reproducible evidence and confidence; a challenger C disputes those findings with typed, code-cited disagreements. The artifact is frozen while they argue. securitycorrectnessspec-complianceperformanceabuseoperationalgovernance
  4. Every objection is reconciled — accepted and fixed, or rejected with evidence. CRITICAL/HIGH items are fixed first and the diff is re-reviewed before the work is called done; unresolved concerns go to a human arbiter.
  5. You customize the repo-specific section; the protocol, its core lenses, and the reviewer–challenger loop stay portable. (Changing the rules is itself a change — see the governance process.)
Why not just prompt for it?

A prompt is a wish. A file is a rule.

  • Persistence

    A prompt is forgotten; a file in the repo binds every future session — provided the agent is configured to read repo convention files, exactly the mechanism that makes AGENTS.md work.

  • Portability

    Any agent that reads repo conventions picks it up with no integration; nothing about the standard is tied to one vendor’s tool.

  • Accountability

    The protocol demands reproducible, severity-rated findings and explicit “checked and clean” verdicts per lens — the difference between a review and a vibe check.

  • Repo-owned rules

    The repo declares its own invariants, known weak spots, and required checks. Generic review becomes this codebase’s review.

Common objections

Fair questions, direct answers

Isn't this just a bigger prompt?

No. It lives in the repo as a versioned file, so every session reads the same rules, and the file itself is something humans and agents can diff, review, and improve. The full argument is above.

Does it work with my coding agent?

Any agent that reads repo convention files can follow it — there is no vendor-specific integration. Agents with a skills directory can install the bundled skill to run the protocol end to end.

Won't three roles burn extra tokens?

Yes: the literature puts adversarial review at roughly 4.5× a zero-shot pass. That cost buys a fix for a measured failure mode — critics agreeing with weak findings, and reviewers yielding to confident but uncited rebuttals. The evidence and the counter-evidence are both linked here.

We already have AGENTS.md. Do we need this too?

They do different jobs: AGENTS.md declares how to work; this declares how to doubt the work. Keep both at the repo root, and fill this file's repo-specific section with your actual checks.

Governance

Review discipline, applied to itself

A standard about review discipline owes its own contributors the same discipline: issues are opened and accepted before any PR, every commit is cryptographically verified (SSH or GPG signed), and every merge to main carries an NCO signoff — a named non-commissioned officer of record who independently reviewed the change and takes responsibility for it. Full process: CONTRIBUTING.md.

Research basis

The evidence behind the protocol

The empirical claims behind this protocol — about self-review, independent challenge, agreement, evidence, and re-review — are traceable to published work. Design choices such as the round cap and the NCO escalation path are recorded in the rationale, not derived from these papers. The list below covers agentic adversarial review and the mechanisms it depends on; the annotated bibliography with relevance notes lives in the repo.

The direct source is Qiu and Gill's Adversarial Review: a reviewer and a critic of that review, with the artifact frozen during the exchange. Their results are also a warning. Naive reviewer–critic agreement scored lower than simpler methods on a review benchmark; only explicit, evidence-typed disagreement fixed it. That is why this standard treats agreement as neither evidence nor a verdict.

Read the counter-evidence too: Smit et al. and Choi et al. find that much of the benefit attributed to debate comes from cheaper ensembling or voting, and Ma et al. find that debate can amplify judge bias. This is why the standard's protocol is about evidence and explicit disagreement, not about adding agents for their own sake. Since v1.1.0 the reviewer–challenger loop is the default; the decision and its counter-evidence are recorded in docs/v1.1-rationale.md.

Citation note: a widely shared industry write-up links Du et al.'s debate paper to arXiv:2305.19118, which is actually Liang et al. The correct ID for Du et al. is arXiv:2305.14325. All IDs above were checked against arXiv metadata on 2026-11-24.
